# X.509 certificate parsing

`sw/apps/web/der.c` and `x509.c`: reading a certificate. Part
one.

See [tls.md](tls.md) for the handshake this feeds, and
[web_app.md](web_app.md) for the browser.

> **This is parsing only.** Nothing here verifies a signature.
> `x509_parse()` reports what a certificate *claims*; it says nothing
> about whether the claim is true. Until chain validation exists, a
> parsed certificate was a decorative object and the connection
> authenticated nothing. That is no longer the case: see "Signature
> verification" below.

---

## Why the parser is its own phase

A certificate arrives from whoever answered the connection, **before
anything about them has been verified**. It is the first
attacker-controlled structured input this browser touches.

Historically that is where TLS implementations break, and the bugs are
not subtle logic errors — they are integer overflows in length
arithmetic, unbounded recursion on nested structures, and readers that
accept BER forms the verifier then disagrees with, so the bytes that
were parsed are not the bytes that were signed.

Those are memory-safety bugs, they are testable exhaustively on the
build machine, and none of them need a network. Finishing and fuzzing
the reader first means that when verification is added, a failure
there is a failure of the logic rather than of the ground underneath
it.

## What the DER reader refuses

Stricter than X.690 requires, and each rule closes one of the above.

| Refused | Why |
|---|---|
| Indefinite lengths | BER, not DER. A certificate using one is malformed, and accepting it is how a signature ends up covering different bytes than the parse did. |
| Non-minimal lengths | DER requires the shortest form. Two encodings of one value is the shape of every signature-bypass bug in this area. |
| Leading zeros in a length | Same. |
| Lengths above 2^24 | So that every length addition is provably free of overflow on a 32-bit machine, rather than checked after the fact. |
| High-tag-number form | X.509 uses none. Accepting a form nothing legitimate uses only widens what a certificate can say. |
| Negative or non-minimal INTEGERs | No field read here has a meaning when negative. |

And structurally: **no allocation** — every field is a view into the
caller's buffer — and **no recursion**. Nesting is walked with explicit
cursors, so a certificate a thousand SEQUENCEs deep costs a thousand
iterations rather than a thousand stack frames on a 64KB stack.

## What the certificate parser refuses

- **A critical extension it does not understand.** That is what
  "critical" means. Name constraints are the case that matters: a CA
  restricted to one domain, whose restriction this browser cannot
  enforce, must not be treated as unrestricted.
- **A mismatch between the inner and outer signature algorithm.** The
  inner one is covered by the signature and the outer one is not, so
  an attacker can rewrite the outer freely. Believing it is how a
  verifier is talked into a weaker algorithm than the issuer chose.
- **RSA keys under 2048 bits.**
- **Trailing bytes** after the certificate, or inside it.
- **EC keys that are not P-256**, and compressed points.

## Hostname matching

RFC 6125, and deliberately narrow:

- **No CN fallback.** A certificate with no `subjectAltName` matches
  *nothing*, whatever its Common Name says. The fallback is deprecated,
  every mainstream browser removed it, and it is the mechanism behind a
  long list of certificate-confusion bugs. No public CA has issued a
  SAN-less certificate this decade.
- **Wildcards cover exactly one whole leftmost label.** `*.a.com`
  matches `www.a.com` and not `a.b.c.com`, and not `a.com` itself.
  `www*.a.com` is refused.
- **`*.com` is refused.** The check is a heuristic — at least two dots
  after the wildcard — because a real public-suffix list is tens of
  kilobytes. It errs toward refusing.
- **An embedded NUL anywhere in a name is refused.** That is the
  classic `www.bank.com\0.attacker.com` attack: one string to a parser
  that respects the length, another to anything using `strcmp`.
- **No IP address SANs.** This browser cannot verify an IP literal
  usefully and does not pretend to.

## The clock problem

`x509_valid_at()` takes a time. The board has no battery-backed clock,
so that time comes from NTP (`sw/common/zntp.h`) and may be absent
entirely on a machine that has not reached a time server.

That is a decision for the caller and it is not a comfortable one.
Refusing every certificate when the time is unknown makes the browser
useless on a LAN with no NTP; accepting an expired one silently
removes the only protection against a certificate whose key has since
been compromised. **Settled: refusing.** `verify_chain()` treats a `now` of 0 as a
failure and says so. `net` runs NTP, so a machine that can browse has
a clock; one that cannot is told to fix it rather than quietly given
a weaker guarantee.

## Testing

```
make test        parses the corpus, checks the refusals
make test-asan   the same, under AddressSanitizer and UBSan
```

`tests/certs/` holds real certificates from a real toolchain, built by
`tests/gen_certs.sh` — an RSA leaf, a wildcard leaf, a P-256 leaf, a
CA with `pathlen`, an expired certificate, and one with a Common Name
and no SAN. Real output, not hand-written DER, so the parser meets the
encodings nobody would think to write by hand: the implicit v1 version
field, the leading zero on a modulus whose top bit is set, `keyUsage`
with a non-zero unused-bit count.

The last part of the suite is a **mutation sweep**: take a good
certificate, corrupt one byte, parse, repeat for every byte and three
bit patterns. About 7,500 deliberately malformed certificates in
around a second. The requirement is not that any particular mutation
be rejected — many produce a certificate that is well-formed and
merely says something different — but that the parser always
terminates and that every view it returns lies inside the buffer.

Plain, that catches crashes and hangs. Under `test-asan` it catches
every read past the end of a buffer, which is the whole class of bug
that matters here.

## Bugs this found

**`keyUsage` bit order.** X.509 numbers `keyUsage` bits from 0, and
DER puts bit 0 in the *most significant* position of the first octet —
so `keyCertSign`, bit 5, is mask `0x04` of byte 0, not `0x20`. Reading
the octet as a little-endian bitmask gives the wrong answer for every
usage that is not symmetric. The visible symptom is a CA that appears
not to be allowed to sign certificates, which during chain validation
would have looked like a chain-building bug rather than a parsing one.

**An empty BIT STRING was accepted.** Legal DER, meaningless as a key
or a signature, and letting one through hands the layer above a
zero-length signature to "verify".

## Signature verification

Parsing says what a certificate claims. These say whether the claim
is true.

| File | What it does | Tested by |
|---|---|---|
| `bignum.c` | Montgomery modexp, up to 4096 bits | `test_rsa.c` vs Python's `pow()` |
| `rsa.c` | PKCS#1 v1.5 and PSS verification, SHA-256 | `test_rsa.c` vs OpenSSL signatures |
| `ecdsa.c` | ECDSA on P-256 and P-384 | `test_ecdsa.c` vs OpenSSL signatures |
| `sha384.c` | SHA-384, on Monocypher's SHA-512 | `test_sha384.c` vs FIPS vectors |
| `verify.c` | chain walk, hostname, dates, root anchor | `test_verify.c` vs a real chain |

**Verification only.** No signing, no key generation, nothing that
touches a secret — which is what lets both `bignum.c` and `ecdsa.c`
skip constant-time discipline entirely. Every value they handle is
public: a public key, a signature off the wire, a hash of data the
attacker already has. That is a claim about this use, not about RSA
or about the curve, and it stops being true the moment anything here
is pointed at a private key.

**Both RSA schemes, because both are unavoidable.** TLS 1.3 only
permits PSS for handshake signatures, so `CertificateVerify` is
always PSS — but certificates are signed by CAs whenever they were
issued, and the installed base of PKCS#1 v1.5 intermediates and roots
is enormous. PSS alone would fail on almost every real chain.

### What it costs

Measured on Lakritz, not extrapolated:

| | software | with `rtl/montmul.v` |
|---|---|---|
| ECDSA P-384 | 12.1 s | **2.7 s** |
| ECDSA P-256 | ~2.5 s | **1.6 s** |
| RSA-2048 | 1.5 s | not accelerated |
| RSA-4096 | 5.5 s | not accelerated |

The block is a 384-bit Montgomery multiplier, so it covers both
curves and neither RSA size. See
[crypto_hw_options.md](crypto_hw_options.md) for why widening it does
not help as much as it looks.

ECDSA verification costs *more* than RSA verification, which surprises
people who know that ECDSA signing is far cheaper. RSA verification
gets to use a tiny public exponent — 17 modular multiplications for
e=65537 — while ECDSA has to do a full 256-bit double-scalar
multiplication regardless. Shamir's trick roughly halves that and is
used.

Roughly half the RSA cost is computing R² mod m, which is the honest
price of avoiding division. `ecdsa.c` uses Montgomery reduction where
p is a Solinas prime with a much faster dedicated reduction. Both are
the obvious optimisations if profiling asks; neither was done first,
because getting Montgomery wrong is loud and getting Solinas
reduction wrong is subtle.

### Bugs these found

All three were invisible to any test built from realistic inputs.

- **`R mod m` derived as `R - m`.** Correct only when the modulus's
  top bit is set — which every RSA modulus satisfies. It passed at
  512, 1024, 2048 and 4096 bits and returned *zero* for a modulus of
  497. Nothing in a certificate would ever have reached it.
- **PSS masked bits checked instead of cleared.** RFC 8017 says to
  *check* `maskedDB`'s top bits and *clear* DB's; the first version
  did the reverse. It passed at 2048 bits and failed at 3072 purely
  because one mask bit differed. That is why the vectors carry two
  key sizes.
- **Oversized base refused by limb count rather than value**, so
  `0xffffffff` against a modulus of 497 came out wrong instead of
  rejected. For RSA, `s >= n` is an invalid signature, and reducing
  it would accept what the standard rejects.

### Anchoring early

The walk stops at the **first** certificate whose issuer the local
store recognises, and ignores whatever the server sent after it.

That is ordinary path building, and here it is worth real time:
en.wikipedia.org sends four certificates, and walking all of them
cost four signature checks — three of them P-384 at about 15 seconds
each on this CPU. Anchoring at the first recognised issuer cuts it to
two.

It is also the more correct behaviour. The trust anchor is the one in
the local store, not whatever the server chose to append; extra and
cross-signed certificates beyond the anchor are exactly that.

It saves WORK, never a CHECK — `tests/test_verify.c` verifies that a
tampered leaf below the anchor is still caught.

### The chain walk

`verify.c` checks, in order: hostname, then dates, then each
signature, then the anchor. Hostname first is deliberate — a valid
certificate for *another* domain is the likeliest thing an attacker
holds, and there is no reason to spend three signature verifications
discovering it.

The anchor carries the whole weight: the last certificate the server
sent must be signed by something in the LOCAL store. A self-signed
root supplied by the server is worth nothing, and is the simplest
forged chain there is.

`tests/test_verify.c` builds real chains with OpenSSL
(`tests/gen_chain.sh`) and every negative case is a named attack: a
certificate for another host, a self-signed root from the server, an
unknown root, a **non-CA certificate used as an issuer** (the single
most damaging X.509 bug — it lets anyone holding any valid
certificate mint one for every domain), a tampered `tbsCertificate`,
an expired certificate, and a missing clock.

Each rejection is also checked to carry a *reason*. A validator that
returns false with no message has failures that cannot be told apart
from bugs.

### No clock means no connection

`verify_chain()` treats a `now` of 0 as a failure, not as permission
to skip the date check. An expired certificate is the normal state of
one whose key has since been compromised.

`z_rtc_valid()` says whether the clock has been set, and `net` runs
NTP, so in practice a machine that can browse has a clock. One that
does not gets told to fix it.

## Wired in

`tls.c` buffers the `Certificate` message (its own 12KB buffer — it is
the one handshake message routinely larger than everything else put
together), parses the chain, checks `CertificateVerify` against the
leaf's key, and calls `verify_chain()` before the handshake is
allowed to complete. Reaching `Finished` without both having
succeeded is itself an error, since a server that skipped a message
would otherwise get a connection that authenticates nothing.

The chain is verified as soon as `Certificate` arrives rather than at
`Finished`, so a bad chain does not also cost a signature
verification.

See [tls.md](tls.md) for the root store and the live tests.
