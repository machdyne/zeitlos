# info

A system monitor. `sw/apps/info`.

```
> run wm
> run info
```

Shows what the machine is — the Zeitlos wordmark, the OS version, the
gateware's feature bits — and what it's doing: memory, SD card, load,
uptime and a process list, refreshed once a second.

## Two goals in tension

This app is a showcase, and it's also the kind of thing people leave
open. Those pull against each other, so everything here is chosen to
make it cheap to leave running:

- **Every figure comes from a syscall that already existed** and copies
  a fixed, small amount: `z_mem_stats()`, `z_proc_list()`,
  `z_uptime_ticks()`. Nothing is polled in a loop, and nothing can
  block.
- **It blocks between samples** with `z_proc_wait()` rather than
  spinning. That matters more here than anywhere else in the tree: a
  status display that busy-waited would distort the very load figure it
  reports, and would show up in its own chart.
- **A full repaint happens only on `Z_WM_REDRAW`.** The per-second
  update redraws just the live parts. The logo, version and feature
  list never change and are left alone — which is most of the pixels.
- **Nothing is ever cleared and then redrawn.** See "No flash" below.
- **It touches the filesystem not at all.** See "No SD card figure"
  below.
- **No `printf` in the draw path.** Three small helpers
  (`put_u32`/`put_str`/`put_size`) cover everything. newlib's formatter
  is large and slow, and an app redrawing once a second shouldn't pay
  for it.
- **No per-pixel drawing anywhere.** Bars, the chart and the logo all
  go through the blitter.

## The logo

96x18, 216 bytes of `.rodata`, blitted in **one** `z_fb_hw_blit_mem()`
call. It's stored in the framebuffer's own bit order, so there's no
conversion step at runtime.

Generated by `sw/data/images/gen_logo_small.py` from the 512x384
`zeitlos.bin`. Two details worth knowing if you regenerate it:

- **The source is cropped to its ink first.** The wordmark occupies a
  band roughly 239x45 in the middle of an otherwise empty 512x384
  splash. Scaling the whole image spends almost every output row on
  blank space and leaves the letters six pixels tall and unreadable.
- **Downscaling takes "any source pixel set" rather than a majority.**
  The logo is 2030 set pixels out of 196608 — fine strokes on an empty
  field — and a majority rule erases it almost entirely.

## No flash

An early version cleared each line before drawing it, cleared the bar
interior before filling it, and redrew every chart column. All three
leave the area blank for a moment, and at a 1Hz refresh the eye catches
every one — the whole window flashed once a second.

None of them clear now:

- **Text** is drawn with `z_fb_draw_text2()`, which writes a solid cell
  per glyph — foreground where the glyph has a bit, background
  everywhere else. Each character overwrites its own patch in one
  operation, so the line is never blank. Strings are padded with
  spaces to a fixed column count, which is what the clear used to be
  for: a space is a fully background-coloured cell. This costs nothing
  — an opaque glyph blit is the same single blitter operation a
  transparent one is.
- **Bars** write the filled part and the empty part, each once.
- **The chart** scrolls one pixel left with a single VRAM-to-VRAM blit
  and draws only the newest column.

That last one is safe despite the overlap: `z_fb_hw_blit_vram()` copies
top-to-bottom, left-to-right, and for a left shift the destination
trails the source in that order, so every word is read before it's
overwritten. A right shift would not be safe. When the chart's full
scale changes, every existing column is at the wrong height, so it
falls back to a full redraw rather than scrolling the old scale along.

## No SD card figure

It was there and it was removed, and the reason is not performance.

**There is no card-detect line on this hardware** (SPI only), and no
mechanism anywhere to remount a volume: `sdmm.c` sets its status once
in `disk_initialize()` and nothing ever sets it back, so FatFs never
re-mounts either. A card is mounted exactly once, at boot, forever.

Any capacity figure this app showed would therefore be a boot-time
snapshot that could not be refreshed, could not notice a card being
swapped, and would read "no card" permanently on a machine booted
without one. A monitor showing a number it cannot keep true is worse
than a monitor not showing it.

Bring it back when there is a remount path. `fs_df()` itself is fine
and the shell's `df` still uses it.

### What it did and didn't cost

Worth recording, because it was briefly and **wrongly** blamed for a
recurring multi-second stall.

`fs_df()` reaches `f_getfree()`, which walks the entire FAT the first
time it is asked. But FatFs caches the result in the mounted `FATFS`
(`ff.c`: *"If free_clst is valid, return it without full FAT scan"*),
maintains it incrementally on every cluster allocation and free, and
the volume stays mounted for the life of the system. So it was a
one-off startup cost, not a per-call one, and it cannot have been
causing repeated stalls.

`k_fs_df()` did call `f_getfree()` **twice** — once via `fs_total()`,
once via `fs_free()` — paying for two scans to get two numbers that
come out of one. `fs_df_kb()` (`sw/os/fs/fs.c`) now does it in a
single call. That fix stands on its own and speeds up `df` and
anything else that asks.

**The cause of the observed stall is still unidentified.** Nothing in
this app's periodic path touches the filesystem now, so if it recurs,
it is somewhere else.

The tick arithmetic is integer (`MS_TO_TICKS`). It was a float
constant, which on a no-FPU rv32im build pulled in the soft-float
routines to compute something exact in integers.

## CPU

Real per-process accounting. The kernel charges each KTIMER tick to
whichever process it interrupted (`z_proc.cpu_ticks`, `sw/os/kernel.h`)
and `z_proc_list()` reports the running total; a percentage is the
**difference** between two samples divided by the elapsed ticks
between them.

This replaced counting runnable processes, which said how many things
*wanted* the CPU but nothing about who was getting it.

Three details that matter:

- **Sampled at ~732Hz.** Work that starts and finishes between two
  ticks is invisible. Fine over the one-second interval used here;
  don't trust a single 100ms reading.
- **A process seen only once reports nothing.** With no previous
  sample, its lifetime total is everything it has used since it
  started, which clamped to the interval comes out as a confident
  100% — every freshly launched app would flash full-CPU for a
  second. It reports 0 until there are two samples to compare.
- **The subtraction is unsigned**, so it stays correct across the
  32-bit wrap of `cpu_ticks` (~68 days of solid CPU). The clamp stays
  anyway, because a pid can be *reused* by a different process between
  two samples and then the difference is against a stranger's counter.

The chart is a fixed 0–100% scale. It autoscaled at first, which was
actively misleading: an idle machine's noise got stretched to full
height, so the display looked alarming when nothing was happening, and
two screenshots a minute apart couldn't be compared.

`ps` at the shell shows the raw lifetime tick count instead — it's a
snapshot with no second sample to difference against.

## Process names## Process names

`z_proc_info_t` gained a `name` field for this. The process table has
never held one — a process is started by filename and identified by pid
thereafter — but a list showing nothing but numbers is close to useless
to a person.

The names come from the pid registry via a new
`k_pidreg_name_for(pid)`. Only apps that call `z_pid_register()` appear
by name (`wm`, `net`, `repl`, `term`, `portdemo`); the rest show `-`
and their pid.

`Z_PROC_FLAG_ACTIVE`/`_DIE`/`_BLOCKED` also moved from `sw/os/kernel.h`
to `sw/common/zproc.h`, because an app receiving those flags needs to
be able to interpret them and `kernel.h` isn't includable from app
code. `kernel.h` now includes `zproc.h`, so there's one copy rather
than two that agree by convention.

## Version

`Z_OS_VERSION` in `sw/common/zeitlos.h`, currently `"0.0.2"`. One
string, in one place, because a boot banner or an `about` command would
want the same value rather than its own copy.

Deliberately no build date or git hash: both change the binary on every
rebuild, which makes "is the flashed image the one I just built?"
harder to answer by comparison, not easier.

## Layout

Narrow on purpose — a status panel meant to sit alongside real work.
Resizable upward; the process list takes whatever vertical space is
left, minus the resize grip's corner so the window stays resizable.

The feature list wraps to however many lines the enabled bits need at
the current width, computed rather than assumed, since which features
exist varies per board.

## Known limits

- **The load figure is a sample, not an integral.** A process that
  becomes runnable and blocks again between two samples is invisible.
  Fixing that properly means counting scheduler ticks per process in
  the kernel, which would give real per-process CPU percentages — the
  natural next step if this needs to be more than indicative.
- **No storage figures**, until there is a way to remount a card. See
  above.
