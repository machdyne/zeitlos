# The card layout

## Status

**Implemented.** This is the directory structure of the SD card from
**v0.0.6** on, and a card the release writes has it. Every fixed
location is named in one registry, `sw/common/zpaths.h`, which the
kernel, the apps, the release tool and the ask pack builder all read.
How it was done is "Implementation" at the end.

There is **no migration**. A v0.0.6 card is written fresh. Nothing in
the kernel or any app looks for a file at its pre-v0.0.6 location, so
no fallback code ships and none has to be removed later.

## The tree

```
/
├── apps/              programs, one flat file each
│   ├── web
│   ├── zcc
│   └── ...
├── data/              everything else an app has, one folder per app
│   ├── web/           roots.der, pins.txt
│   ├── zcc/           libz/, examples/
│   ├── tts/           speech/en.spk
│   ├── casino/        bank.dat
│   ├── ask/           <pack>/ -- ask's indexes
│   └── ...
├── sys/               the system's own files
│   ├── zeitlos.cfg
│   └── version
├── docs/              the documentation, as released
├── media/             example media, and yours
│   ├── audio/
│   └── images/
├── home/              yours. Empty on a new card.
├── opt/               large optional data packages
│   └── ark/<pack>/
├── tmp/               scratch, gone at the next boot
├── ram/               the ramdisk (a mount, not a directory)
└── usb/               USB storage (a mount, not a directory)
```

## The rules

1. **Every app is installed in exactly two places:** `/apps/<name>`, its
   program, and `/data/<name>/`, everything else it has. "Everything
   else" covers both what it shipped with (`roots.der`, `en.spk`,
   `libz/`, examples) and what it wrote itself (`pins.txt`, `bank.dat`,
   logs, caches). Removing an app means deleting those two things, and
   nothing of it is left anywhere else.

2. **Shared data still has an owner.** Data used by more than one app
   lives in the folder of the app that owns it, and the others read it
   from there. An app may read another app's `/data` folder in the same
   way it may read another app's memory. A dependency on another app is
   then easy to check: `/data/web/` exists or it does not.

3. **Data that no app owns belongs to the system** and goes in `/sys`.
   It is made by the kernel or by the release tool, **never by a build
   in `sw/apps/`**. If something is generated by an app's Makefile, it
   is that app's data. That is the test.

4. **`/home` is the person's.** A release puts nothing in it, and the
   system never creates folders inside it. People arrange it however
   they like.

5. **Apps only write in their own `/data/<name>/`, in `/tmp`, and
   wherever the person tells them to.** A save dialog is the person
   telling them; its default starting place is `/home`. Apps never
   write in `/apps`, `/sys` (the settings app and the kernel are the
   exceptions for `zeitlos.cfg`), `/docs` or `/opt`.

6. **Names are lowercase and natural.** Long file names are enabled
   (`FF_USE_LFN 1`, `sw/os/fs/fatfs/ffconf.h`), so 8.3 shortenings are
   gone: `blackjack`, not `blkjack`. FAT is case-insensitive, so
   lowercase is a convention for display, not a requirement for opening.

## Each top-level folder

### `/apps`

One file per program, named after its directory in `sw/apps/`:
`sw/apps/web/web.bin` is installed as `/apps/web`. No extension.

It is **flat on purpose**. The dock and any launcher list the installed
apps with a single directory read, and `run web` resolves with a single
`f_open()`. A folder per app would turn both into one directory open per
app, on a card reached over SPI.

The core apps (`wm`, `net`, `term`, `console`) live in the flash archive
and are **not** in `/apps` on a released card. A copy placed there
deliberately takes precedence over the flash copy (see "Finding a
program"). Their data folders are on the card like any other app's:
`/data/net/net.cfg`.

### `/data/<name>/`

The name is the program name, the same one used in `/apps`. App names
are already one global namespace (`run`, the dock, pidreg), so they need
no prefix to stay unique.

A data folder holds three kinds of file, which differ only when it comes
to upgrades (see "Upgrades"):

| kind | examples | made by |
|---|---|---|
| shipped, replaced on upgrade | `zcc/libz/`, `tts/speech/en.spk`, `web/roots.der` | the app's build, copied by the release tool |
| shipped, kept once edited | `bbs/bbs.cfg`, `fed/fed.cfg` | the app's build or tree, copied by the release tool |
| the app's own | `casino/bank.dat`, `web/pins.txt`, `cron/state` | the app, at run time |

Caches go in `/data/<name>/cache/`. Anything in a folder of that name
can be deleted at any time without losing anything. Scratch that need
not outlive the app goes in `/tmp` instead.

An app that writes creates its own data folder if it is missing --
`z_data_file()` (`sw/common/zdata.h`) does that for it. The release
creates the folders it ships files into.

### `/sys`

Files that belong to the system rather than to any app:

| file | what | made by |
|---|---|---|
| `zeitlos.cfg` | system configuration (`docs/config.md`) | release tool (template, every setting commented out); edited by the settings app and by hand |
| `version` | which release this card was written by | release tool |

`/sys` is meant to be looked at. It is small, and it is where the
settings are.

The kernel makes sure `/sys`, `/home` and `/data` exist whenever it
finds the card up (`fs_layout_prepare()`, `sw/os/fs/fs.c`), so a card
formatted by hand, or with `format`, works too: the settings app can
write its file, a save dialog has somewhere to open, and an app can make
its data folder.

### `/docs`

The documentation, as it was in the release that wrote the card: this
tree's `docs/*.md`, copied as is. It is plain files for reading, and it
is **separate from** the ask pack built from the same source (see "Ask
and Ark"). `/docs` exists without ask, and ask's copy is in ask's own
format.

Release-owned, like `/sys/version`: replaced on upgrade.

### `/media`

Example media, plus the place a person may keep their own:

```
/media/audio/    *.mod, *.mid -- track, play, midi
/media/images/   *.jpg, *.pgm, *.svg -- view, the demos
```

A release adds and replaces only the files it ships. Anything else in
`/media` is the person's and is left alone. `track`, `play` and `midi`
list `/media/audio` and then `/home`; anywhere else, open the file from
the file browser.

### `/home`

Empty on a new card. Save and open dialogs start here, and so does a
`posix` shell. The file browser starts one level up, at the top of the
card, where `/apps`, `/data`, `/home` and `/media` are all in view.

The one thing the system itself writes here is a screenshot (`ss` at the
console), because it is something the person explicitly asked for:
`/home/ss.bin`.

### `/opt`

Large, optional data packages that do not belong to any single app. They
are installed separately from the release's own files and can be large
enough to need a bigger card.

Currently that means the Ark library only, `/opt/ark/<pack>/`.

### `/tmp`, `/ram`, `/usb`

`/ram` and `/usb` are mount prefixes that `sw/os/fs/fs.c` rewrites into
FatFs volumes (`docs/ramdisk.md`, `docs/usb_host.md`). They are not
directories on the card, and a directory of either name at the card root
cannot be reached.

`/tmp` is scratch space that does not survive a reboot:

- **A board with a ramdisk** maps `/tmp` onto the ramdisk the same way
  `/ram` is mapped, so `/tmp` and `/ram` are the same volume. Nothing
  written to `/tmp` reaches the card.
- **A board without one** (1MB of main memory or less, `docs/ramdisk.md`
  "Sizing") uses a real `/tmp` directory on the card, which the kernel
  empties at boot.

Either way, an app writes to `/tmp` and never has to check which kind
it got. `web`'s page spool and the `.args` files used to pass command
lines to `zcc`, `vi` and `zfpga` live here. With a ramdisk, `ls /`
shows both `ram` and `tmp`: two names for one volume.

## Finding a program

A **bare name** (a dock icon, `z_proc_run("poker")`, boot starting
`wm`) is looked up:

1. `/apps/<name>`
2. the flash archive, under `<name>`

and nowhere else. To hot-swap a core app during development, put the
new build at `/apps/wm` (for example `xf apps/wm`) and reboot; delete it
to go back to the flash copy.

**A shell looks in its working directory first.** Typed at a shell, a
bare name is tried there before `/apps` and flash:

```
$ cd proj
$ zcc -o test test.c
$ test                  runs /proj/test, even if /apps/test exists
```

`posix` does this with its own working directory; the kernel shell's
is always the root, so `tget loom wm` then `run wm` runs the `wm` just
fetched. Only a real executable counts -- a data file never stands in
for a program -- and when one hides an installed program of the same
name the shell says so (`test: running /proj/test, not the installed
one`).

Unix leaves the working directory out of the search and makes you type
`./test`, because on a shared machine someone else's file could pose
as a command. Zeitlos is single-user, so that reason does not apply,
and "the program I just made is the one that runs" is what people
expect. Only shells do this: boot, the dock and one app starting
another have no working directory and use `/apps` and flash alone, so
a file left anywhere on the card cannot change what they launch.

A **name containing `/`** is a path. The kernel opens it exactly as
given, from the root; `posix` first resolves it against its working
directory, so `proj/test` and `./test` mean what they would on Unix.
That is also how the file browser launches a program that is not
installed.

`ls` and `ls /apps` list the flash archive's programs after the card's,
under `in flash:`, leaving out any that `/apps` shadows.

This is `fs_exec_resolve()` in `sw/os/fs/fs.c` for the search everything
shares, `run` in `sw/os/sh.c` and `bi_run()` in `sw/apps/posix/sh.c` for
the shells' working-directory step. Archive names stay flat
(`sw/os/zar.h`).

Four of these look like exceptions but are not:

- **The casino's games** (`poker`, `roulette`, `blackjack`, `slots`,
  `craps`) all read and write `/data/casino/bank.dat`. The bank belongs
  to `casino`, which launches them. This is rule 2 (shared data with an
  owner), not five apps sharing a folder that nobody owns.
- **`chip8.cfg` stays next to the ROMs**, wherever the person keeps
  them. It is part of a ROM pack, not chip8's own state: one file that
  travels with a directory of ROMs and says what each one needs
  (`sw/apps/chip8/config.h`). chip8's screenshot (`chip8ss.zbm`) is
  written into the same directory, because the person chose that
  directory by loading a ROM from it (rule 5).

  chip8 ships with a ROM of its own, in `/data/chip8/roms/`, from
  `sw/data/chip8/roms/` in the tree. Its open dialog starts there.
  `redoct.ch8` is an XO-CHIP demo; at 65,000 bytes it is too big for
  anything else, so chip8 picks the XO-CHIP profile by itself and the
  folder needs no `chip8.cfg`.
- **ls99's per-module folders** (`/bench/<name>/` before, where a
  bench netlist's LS-99 keeps its files) are ls99's data, so they move
  to `/data/ls99/<name>/`. The netlists themselves are the person's
  and go wherever they save them.
- **BASIC's programs are in BASIC's folder**, `/data/basic/`, not in
  `/home`. BASIC is a computer of its own: `LOAD`, `SAVE` and `DIR` see
  one flat directory, its disk, and nothing outside it
  (`docs/basic_app.md`). That disk is the app's storage, like an LS-99's
  folder; the examples ship on it, and a `.BAS` file can be copied in or
  out of it with the file browser.

## Ask and Ark

The Ark library and ask's indexes of it are kept apart, because they are
used differently:

- **`/opt/ark/<pack>/`** holds the documents: what `read` opens and what
  a person can browse with `files` without ask. Keeping them in `/opt`
  makes them easy to find and leaves them useful on their own.
- **`/data/ask/<pack>/`** holds ask's index of that pack (`index.zak`
  and the files beside it). Nothing but ask reads it, so it is ask's
  data.

The two halves of a pack are matched by name: `/data/ask/arklite/`
indexes `/opt/ark/arklite/`. Installing a pack means writing both, and
removing it means deleting both.

`zdocs` follows the same rule. Its documents go to `/opt/ark/zdocs/`
like any other pack's, and `/docs` stays separate: `/docs` is the plain
release copy, and `/opt/ark/zdocs/` is the corpus as ask's pack builder
prepared it (`tools/ask/dist/zdocs.spec`).

**A pack holds no card path.** Its index stores each document's path
relative to the pack's own folder (`books/00000072.md`), and `ask` puts
`/opt/ark/<pack>/` in front when it loads the pack. So a pack works
wherever the registry says packs go, and moving them again would not
invalidate a pack already built. `tools/ask` reads the same registry
only to lay out what it builds as the card is -- `out/<pack>/opt/ark/`
and `out/<pack>/data/ask/` -- so that installing one by hand is
`cp -r out/<pack>/* <card>/`.

## What changes for an app

When writing or changing an app:

- **Files it ships with** go in its tree in `sw/apps/<name>/` and are
  listed for the release tool with a `/data/<name>/…` destination.
- **Files it writes** are named with `z_data_file()`
  (`sw/common/zdata.h`), which returns `/data/<name>/<leaf>` for the
  calling app and creates the folder on first use. An app does not spell
  out `/data/<name>` itself. `<name>` is `Z_APP_NAME`, which
  `sw/common/app.mk` defines as the app's `APP`.
- **Another app's files** are read by their full path, written as a
  constant in `sw/common/zpaths.h`, the one registry of fixed paths. An app that relies on another app's data checks that the
  file exists and says which app is missing if it does not.
- **Its save and open dialogs** start in `/home` unless the person has
  already been somewhere else in this session. `z_dialog_open()` and
  `z_dialog_save()` given no directory start there. An app that ships
  things to open starts its open dialog in them instead -- bench in
  `/data/bench/examples`, chip8 in `/data/chip8/roms` -- because on a
  new card `/home` is empty.
- **Messages name places by the registry too**: `"could not read "
  Z_CFG_PATH`, not `"could not read /sys/zeitlos.cfg"`. `zrelease check`
  finds a card path anywhere in a string literal, not only at its start.
- **It never creates folders in `/home`.**

## The release tool

`release/lib/mkfatimg.py` writes the card, and is the only thing that
does. With this layout it:

- creates the top-level folders, and the `/data/<name>/` folders for the
  apps it ships data for;
- copies each app to `/apps/<name>` under its natural name;
- copies shipped app data to `/data/<name>/`;
- writes `/sys/zeitlos.cfg` (the template) and `/sys/version`;
- copies `docs/*.md` to `/docs`, the example media to `/media`, the Ark
  scroll to `/opt/ark`, and the requested ask packs to
  `/opt/ark/<pack>/` and `/data/ask/<pack>/`;
- makes `/home`, and leaves it empty;
- puts nothing else at the card root.

Its destinations come from the same registry the C code uses
(`sw/common/zpaths.h`, read by `release/lib/zpaths.py`), so the card
and the code cannot disagree about where a file is. Directories are
made as the first file that needs one is copied, so there is no list
of them to keep in step either.

## Upgrades

**Not implemented.** Today a new release means writing a new card. This
section records how in-place upgrades are planned to work, so that
nothing in the layout gets in their way.

The principle is that **an upgrade replaces only what changed and
touches nothing it did not ship.** `/data/casino/bank.dat`, an edited
`/data/bbs/bbs.cfg`, and everything in `/home` survive.

The plan:

1. The release tool writes a manifest, for example `/sys/manifest`,
   with one line per file the release shipped: its path, a hash, and a
   policy, either `replace` or `keep`.
   - `replace`: programs, `libz`, `en.spk`, `roots.der`, `/docs`,
     example media, `/sys/version`.
   - `keep`: files people edit, such as `/sys/zeitlos.cfg`,
     `/data/bbs/bbs.cfg` and `/data/fed/fed.cfg`.
2. An updater compares the new manifest with the one on the card:
   - A `replace` file whose hash differs is overwritten.
   - A `keep` file is written only if it is missing.
   - A file in the new manifest that was not in the old one is added.
   - A file in the old manifest that is gone from the new one, and that
     still has the old hash, is removed. If its hash differs, someone
     changed it, and it is left alone.
   - A file in no manifest is never touched.
3. The new manifest replaces the old one last, so an interrupted upgrade
   can be run again.

What the layout already provides for this: shipped and user-made files
can sit side by side in `/data/<name>/` because the manifest tells them
apart. `/home` holds no shipped files at all. Programs are single files.
Ask packs in `/opt` can be upgraded on their own schedule, separately
from the release.

## Why not the Unix layout

POSIX itself requires very little of a directory tree: `/`, `/dev` with
`null`, `tty` and `console`, and a writable `/tmp`. The familiar
`/bin`, `/etc`, `/usr`, `/var` and so on come from the Linux Filesystem
Hierarchy Standard. That standard is built around problems Zeitlos does
not have: many users, permissions, a package manager spreading one
program across `/usr/bin`, `/usr/share` and `/etc`, and several
filesystems mounted together.

Zeitlos keeps the Unix names where the meaning is the same and where a
person can guess them: `/home`, `/tmp`, `/opt`. Everywhere else it uses
words that say what is inside, for people who have only ever used a
phone: `/apps` rather than `/bin`, and `/data` rather than spreading an
app across `/etc`, `/var` and `/usr/share`. The pairing of `/apps` and
`/data/<name>/` follows Android, where each app's files stay together
and resetting or removing an app means deleting one folder.

`/tmp` is real here, and `posix` provides `/dev` inside its own process
(`docs/posix.md`), so what POSIX asks for is covered.

## Alternatives considered

- **A folder per app holding its program as well** (`/apps/web/web`).
  It isolates more, but listing or launching apps then costs a directory
  open per app. A flat `/apps` plus `/data/<name>/` gives the same
  isolation for data at a fraction of the cost.
- **Separating shipped resources from runtime state** (`/apps/<name>/`
  for resources, `/data/<name>/` for state). That would make two places
  per app plus one for the program. The upgrade manifest already tells
  the two kinds of file apart, so splitting the folders gains nothing.
- **`/files` with prepared folders** (`Documents`, `Pictures`, …). That
  imposes someone else's structure on the person's own space. `/home`
  starts empty.
- **`/system` or `/zeitlos` instead of `/sys`.** `/sys` is short and,
  being small and readable, not dangerous to browse.
- **A search path with the card root first and a fallback to the old
  `/apps` layout.** Unneeded once the card is rewritten for v0.0.6, and
  the root stays clean. The root comes back only as the kernel shell's
  working directory, for the kernel shell alone.
- **Unix's rule, `./test` to run a program in the working directory.**
  Its reason is a shared machine; Zeitlos is not one (see "Finding a
  program").

## Implementation

Each phase is delivered with its documentation and an on-board check
list.

**Phase 1: one registry, no change in behaviour. Done.**

- `sw/common/zpaths.h` names every fixed card location: 48 names, each
  `#define Z_NAME "literal"` on its own line, holding **today's**
  values. Names say what a place is for (`Z_DIR_CRON_DATA`), not where
  it is (`/user`), so Phase 2 changes values and no code.
- The kernel and 40 app and common source files use the names instead
  of literals.
- `release/lib/zpaths.py` reads the header. `mkfatimg.py` takes every
  card destination from it, and makes directories as files need them
  rather than from a list of its own.
- `zrelease check` has a "card paths" step that fails on any string
  literal in `sw/os`, `sw/apps` or `sw/common` that is a registry
  value or starts with a card top-level folder (today's and v0.0.6's).
  Host tests and the Linux builds of bbs and fed are not scanned.
  Run against the tree before this phase, it reports exactly the 56
  literals that were converted.
- `sw/data/chip8/roms/redoct.ch8` is in the tree, for Phase 2 to ship.

How it was checked, with the xPack `riscv-none-elf-gcc` 15.2.0-1
toolchain (newlib) and `SOURCE_DATE_EPOCH` fixed so `__DATE__` is
stable:

- **All 68 apps build byte-identical** to the tree before the change.
- **The kernel differs only in `fs.o`.** `fs_exec_resolve()`'s apps
  prefix was `"apps/"` and is now `Z_DIR_APPS "/"`, which is
  `"/apps/"`. The two are the same path to FatFs (`FF_FS_RPATH 0`
  starts every path at the root of its volume). Every other kernel
  object is identical.
- **The card holds the same files at the same paths.** Two differences,
  both intended: `zpaths.h` itself is now among the headers copied to
  `/libz/include` (the headers that include it are there already), and
  an empty `/speech` is no longer made when no speech pack ships.
- `release/lib/test_mkfatimg.py` (real images, formatted and read
  back), `release/lib/selftest.py`, `posix`'s 119 host tests and the
  zcc and zfpga host builds pass.

Two things planned for this phase moved:

- `z_data_file()` comes in Phase 2. Today's locations have no common
  shape (`/user/cron.cfg`, `/web/pins.txt`, `net.cfg`), so a helper
  that builds `/data/<app>/<leaf>` has nothing to return yet.
- `tools/tftp-dist.sh` needs no registry. It publishes programs under
  their bare names to a TFTP server, and never names a card location.

**Phase 2: the v0.0.6 layout. Done.**

The registry's values changed, and with them the card. What else it
took:

- **Kernel** (`sw/os`):
  - `fs_exec_resolve()` looks for a bare name in `/apps`, then flash,
    and no longer in the card root.
  - `/tmp` is a third entry in the mount table: the ramdisk when there
    is one, skipped when there is not, so that it falls through to a
    card directory.
  - `fs_layout_prepare()` makes `/sys`, `/home` and `/data` (and a card
    `/tmp`), and empties a card `/tmp` once per boot. It is called when
    boot finds the card, when a late card comes up during `init`, and
    after `mount` and `format`.
  - The configuration is `/sys/zeitlos.cfg`, and `ss` writes
    `/home/ss.bin`.
  - The core-app probe at boot looks for `/apps/wm`.
  - `ls` and `ls /apps` list flash programs that `/apps` does not
    shadow.
- **`z_data_file()`** in `sw/common/zdata.h`, with `Z_APP_NAME` from
  `app.mk`. `cryptobench` is the first user (`results.txt`); apps whose
  files the release ships or another app reads keep their names in
  `zpaths.h`.
- **Apps**:
  - natural names (`blackjack` in `casino.c`'s game list);
  - the casino bank in `/data/casino`, without the old-path fallback;
  - chip8 and bench open their dialogs in their shipped folders, and a
    dialog given no directory opens `/home`;
  - `track`, `play` and `midi` list `/media/audio`, then `/home`;
  - `web` spools to `/tmp`, which replaces its own choice between
    `/ram` and the card;
  - `net` makes `/data/net` before writing `net.ip`;
  - BASIC's disk and the bench examples' `program=` lines moved to
    `/data/basic`;
  - the demo scripts name `/data/automate` and `/media`;
  - messages that name a place build it from the registry.
- **Release tool**: the card has `/apps`, `/data`, `/docs`, `/home`
  (empty), `/media` and `/sys` -- plus `/ark` and `/ask`, which phase 3
  moved -- and no loose files at the root. `/sys/version` reads `zeitlos
  <Z_OS_VERSION>`. chip8's ROM ships.
- **The lint** now finds a card path anywhere in a string literal
  (`"could not read /zeitlos.cfg"`), not only at its start. That found
  eleven messages the first version had missed.
- **Docs**: every page that named a card path; `flash_apps.md`'s search
  path and shadowing; this page.

Where this phase settled something differently from the plan:

- `web`'s spool is `/tmp/web.spool`, not a file under `/data/web`.
  Scratch for one page is what `/tmp` is for, and `/tmp` already makes
  the ramdisk-or-card choice `web` used to make by probing.
- BASIC's programs live in BASIC's own folder, not in `/home`: `LOAD`
  and `SAVE` see one directory, and the examples have to be in it.
- The file browser starts at the top of the card, not in `/home`.
- The kernel makes `/sys` as well as `/home` and `/data`, because the
  settings app writes there.

How it was checked:

- The kernel and every app build with the xPack toolchain.
- Every app's host test suite (`make test`, 35 of them) passes except
  `hex`'s, which fails to link on the tree before this work too
  (`zwidget.c`'s speech calls are not stubbed there). `sw/test` also
  fails on that tree, for want of `-march` and `-mabi`. Two suites
  needed changes:
  - `posix`'s now `cd /` first, because its fixture tree is a whole card
    and the shell starts in `/home`;
  - `netserve`'s fake filesystem takes the authkeys path from the
    registry.
- `release/lib/test_mkfatimg.py` builds real images and now also checks
  `/sys/version`, `/sys/zeitlos.cfg`, an empty `/home`, chip8's ROM and
  that nothing is loose at the root. It passes, as does `selftest.py`.
- A `base` card built from the tree has the layout above.

**Phase 3: ask and Ark. Done.**

- `Z_DIR_ARK` is `/opt/ark` and `Z_DIR_ASK_PACKS` is `/data/ask`.
- **Packs no longer hold card paths.** The index format is version 2:
  `docs.zdt` stores paths relative to the pack's document folder, and
  `sw/apps/ask/aidx.c` joins them to `Z_DIR_ARK/<pack>` at load. Version
  1 stored `ark/<pack>/...` whole, which tied a pack to one layout; a
  version-1 pack is refused with `index built by another version of
  tools/ask -- rebuild the pack`.
- `tools/ask/lib/cardfs.py` reads both roots from the registry (through
  `release/lib/zpaths.py`) to lay out its output as the card is, and
  `release/lib/mkfatimg.py` copies each half to the path it already has.
- `ask`, `read`, `zask.h`, `test/hosttest.c`, the release notes text,
  `docs/ask_app.md` and `docs/releases.md` follow.

How it was checked:

- `zdocs` and `arklite` build. `strings` over every index file finds no
  `opt/ark` anywhere: the paths are pack-relative.
- `sw/apps/ask/test/hosttest` -- the device's own engine -- loads both
  packs from one merged card tree and returns `/opt/ark/...` paths with
  the same documents and offsets as before. With every file's version
  word set back to 1, it refuses the pack with the message above.
- `release/lib/test_mkfatimg.py` builds the `base` and `arklite` card
  variants (all pack files on the card, nothing loose at the root) and
  passes, as do `selftest.py` and `tools/ask/tests`.
- The kernel and every app build; the lint is clean.
