# DDR3 datapath, second attempt

Written before the Verilog, because the two most expensive faults last
time were a control that reached no hardware and two paths that had to
agree and did not. Both are design-time decisions, not debugging
problems.

Target: Mozart ML2, LFE5U-45F, **MT41K256M16TW-107** (DDR3L, 4Gb,
x16, 1.35V). System clock 48MHz, DRAM clock 96MHz, half-rate
controller.

## 1. What the cache asks for

`rtl/cache_id.v` fills a line with a **4-word linear wishbone burst**
(`DCACHE_LINE_WORDS 4`, `m_cti_o` incrementing, `m_bte_o` linear).

Four 32-bit words is sixteen bytes. On a x16 part a **BL8 burst is
also sixteen bytes**. A line fill is therefore exactly one DRAM read,
with nothing left over and nothing discarded.

That is the single most important fact in this document. Build the
controller around it:

  * **One BL8 read serves one line fill.** Four words out of one
    burst, no second access, no partial burst.
  * The column address of a burst has A[2:0] = 0 by construction,
    which is what BL8 requires anyway.

Stores are **write-through**, so writes still arrive as single 32-bit
accesses with byte enables. Writes are handled in section 4.

### Done: the single-block read buffer

`ddr3_ctrl.v` keeps the sixteen bytes of the burst it just read, with
one tag and one valid bit. A line fill now costs:

```
line fill: 15 cycles for the first word, 3 for the next three
```

One DRAM read and three register reads, against four DRAM reads
before.

It is not a cache. No replacement policy, no configuration, nothing to
tune. **Any write invalidates it** -- deciding which writes overlap the
buffered block is more logic than dropping it, writes are rare next to
fills, and the simple rule cannot be wrong.

## 2. Timing, from the datasheet

MT41K256M16, speed grade -107 (DDR3L-1866), running far below its
rated clock at tCK = 10.417ns. Every parameter is the larger of its
time and clock-count form, which at this clock is always the time
form except where noted.

| Parameter | Datasheet | At 96MHz |
|---|---|---|
| tRCD | 13.75ns | 2 CK |
| tRP | 13.75ns | 2 CK |
| tRC | 46.25ns | 5 CK |
| tRAS | 34ns min, 9 x tREFI max | 4 CK |
| tRFC | **260ns** (4Gb) | 25 CK |
| tREFI | 7.8us | 750 CK |
| tWR | 15ns | 2 CK |
| tRTP | 7.5ns, min 4 CK | **4 CK** |
| tWTR | 7.5ns, min 4 CK | **4 CK** |
| tCCD | 4 CK | 4 CK |
| tMRD | 4 CK | 4 CK |
| tMOD | 15ns, min 12 CK | **12 CK** |
| tXPR | tRFC+10ns | 26 CK |
| tZQinit | 512 CK | 512 CK |
| tDLLK | 512 CK | 512 CK |

**tRFC is 260ns because the part is 4Gb.** The 1Gb value of 110ns was
used for weeks last time; a refresh fires every 7.8us, so waiting the
wrong one issues commands to a DRAM that is still refreshing about
128,000 times a second. The corruption is intermittent and moves with
timing, which reads exactly like a tuning problem.

**tRTP, tWTR, tMRD and tCCD are clock-count minimums**, not times. At
this clock their time forms are far below one cycle and rounding them
from nanoseconds gives zero. Take the max of both forms, always.

### Latencies

CL = 6 and CWL = 6, both EVEN, and that is a constraint of this
design rather than a preference.

The controller is half-rate and issues every command on the same DRAM
clock of the pair. CL and CWL must therefore share a parity: an even
CL with an odd CWL lands read data on a controller-cycle boundary and
write data half a cycle off it, putting the write strobe outside
tDQSS no matter how the datapath is tuned.

CL=6 is the lowest DDR3 defines, so CWL must be even too, and 6 is the
nearest legal value. A controller that issues reads and writes on
different phases can use CWL=5, which is what the part is specified
for at this clock -- but this one does not, and **copying a value from
an implementation that works does not copy the mechanism that makes it
work.**

## 3. The read datapath

### One path for everything leaving the chip

DQ[15:0] and DM[1:0] are generated by **the same logic with the same
timing**, DM treated as two more data bits.

Last time they were separate, and the measurement said they wanted
alignments eight bytes apart: the setting where the data landed
correctly was not the setting where the mask selected the intended
bytes. Two paths that must agree will eventually not.

### SUPERSEDED: capture is at a fixed latency (see ddr3-status.md, round 4)

The section below was written from the first attempt, whose datapath
never worked. On hardware DATAVALID fired without any strobe having
been caught; LiteDRAM's ECP5 PHY, which does work on this board,
captures at a fixed latency. Kept for the record.

### (old) Capture is self-timed, per lane

`DATAVALID` from each `DQSBUFM` says when that lane's FIFO has data.
Capture on it. Do **not** count cycles from the READ command: the
buffer is a FIFO whose fill depends on where the read gate lands, so a
counted tap samples a moving target, and no capture position is then
repeatable.

**Each lane latches on its OWN strobe.** The two buffers are
independent hardware -- own FIFO, own strobe, own pad -- and nothing
makes them deliver in the same cycle. A lane arriving one cycle later
has its beats off by four, which no shared control can correct.

Per-lane, every one of them: gate, capture, bit slip, READCLKSEL.
Last time four separate controls turned out to be wired to lane 0's
value or to nothing at all, and each produced a clean uniform map that
read as "this axis does not matter".

### Assembly lives in its own module

The beat assembly is ordinary synchronous logic and belongs in a file
a testbench can reach. `DQSBUFM` and `IDDRX2DQA` have no simulation
models, so anything tangled up with them can only be observed through
a hardware build and a line of console output.

Every fault found in that path last time was an off-by-one. A
testbench finds those in seconds.

## 4. Writes: read-modify-write, no byte masking

A write-through store is 32 bits with byte enables; a DRAM access is
16 bytes. Something has to bridge that, and there are two ways:

  * **DM**, masking the bytes not being written.
  * **Read-modify-write**: read the sixteen bytes, merge, write all
    sixteen back with nothing masked.

**Take RMW.** Unmasked writes round-tripped byte-exact on hardware
last time; masked writes never worked at any alignment tried. More
importantly RMW has ONE mechanism to get right instead of two, and
that mechanism -- a burst read -- is the same one the line fills
already depend on. If reads work, everything works. If reads do not,
nothing does, and there is a single place to look.

DM is tied inactive: all zeros, write every byte.

The cost is real and should be stated: a store becomes a read plus a
write, roughly 12 controller cycles against 2. The write-through cache
has a posted-write buffer in front of it, so the CPU does not stall on
it, but a store-heavy loop will feel this. Getting it correct first
and fast second is the right order here, and the burst read that RMW
needs is already the critical path for fills.

**RMW is only sound downstream of correct reads.** Do not enable it
until a burst read is byte-exact; merging into a block that was read
wrongly writes the corruption back and destroys data that was fine.

## 5. What must be measurable

Rules, learned expensively:

  * **Before believing a sweep, confirm the axis reaches hardware.**
    If no value of a control changes any output, the control is
    disconnected, not unimportant. Four of them were.
  * **A sweep range wider than the field it writes is not a wider
    sweep.** A 4-bit sweep into a 2-bit field aliases, and the map
    repeats with period four while looking like sixteen measurements.
  * **Sweep for repeatability before correctness.** A read that
    returns the same value twice needs no known-good data, so it works
    even with writes entirely broken.
  * **A stability test that accepts a constant is not one.** A dead
    read returning zero is perfectly repeatable. Seed a known value
    and require a match.
  * **Train with the controller OFF.** A refresh every 7.8us in the
    middle of a scan disturbs a different random subset of points on
    every run, and the maps then disagree between identical
    bitstreams.
  * **A diagnostic must not rewrite what it measures**, and must be
    able to succeed PARTIALLY -- scoring whole words hides one lane
    working while the other does not.
  * **A read must complete even when the PHY never answers.** A
    wishbone cycle that never acknowledges hangs the CPU on a load,
    forever, with no console. Time out, return a marker, set a sticky
    bit. Bad data can be measured; a hang can only be power-cycled.

## 6. Order of work

1. Controller burst support: serve a 4-word CTI burst from one BL8.
   Verify against the checking model, which fails on any protocol
   violation.
2. Fix the testbench's PHY double to follow DQS rather than a timer
   (`rtl/tb/README-ddr3.md`).
3. Write the datapath with the structure above.
4. Bring up READS only, with RMW disabled and writes unmasked, until
   a burst read is byte-exact and repeatable.
5. Enable RMW. Then, and only then, stores.
