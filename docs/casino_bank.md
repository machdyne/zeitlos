# sw/common/games: shared code for the casino apps

Code that more than one game in `sw/apps` needs. Two things so far: the
shared bank, and an unbiased bounded draw.

    cd sw/common/games && make test     # 169 checks

There is no target build here. These are `.c` files that apps compile
into themselves, the same way they already do with `../zwin.c` and
`../zgfx.c`.

## Dice

`zdice.c` holds six faces at two sizes, generated by `gen_dice.py`.

It is here **from the start**, which is a deliberate exception to the
rule below. Cards waited for a second caller because the shape of the
shared thing was a genuine question — which of poker's card code was
general and which was poker's. A die has no such question: six faces,
pips on a fixed three-by-three grid, parameterised by size. There is
nothing a second caller would teach that is not already obvious.

**The body is lit and the pips are dark**, which is what a real die
looks like and also what makes a die *opaque*: rolled over anything it
covers what was there, so no clear is needed and nothing flickers. A
dark die with lit pips would need the background cleared first, and
clearing is what makes an animation flash.

The test **counts the pips out of the bitmap** rather than comparing
against a second copy of the layout. Every pip is the same disc, so the
dark area inside a die's body is exactly the face value times one pip —
which catches a missing pip, a doubled one, or a face wired to the wrong
arrangement, without the test knowing where any of them go.

That only works because the pip centres are rounded to whole pixels. A
fractional centre makes each disc a slightly different shape depending
on where it lands, so the pips come out visibly unequal *and* the
invariant stops holding. Both were fixed by the same line.

## What belongs here

**Anything in here must be useful to more than one app.**

`zcard.c` (the encoding), `zcardart.c` (the tiles) and `zdeck.c` (the
shoe) were `sw/apps/poker`'s until blackjack became their second
caller. That is the point at which the shape of a shared thing is known
rather than guessed — promoting code for a caller that does not exist
is how a shared directory becomes a junk drawer.

**`pk_eval.c` stayed in poker.** Blackjack totals a hand, it does not
rank one, so a poker hand evaluator here would be a shared file with a
single user. What the two games genuinely have in common is the
encoding, the pictures and the shuffle.

Two things improved in the move:

- **`zdeck` holds a shoe of up to eight decks**, because blackjack
  deals from six. Poker asks for one. The cost is 420 bytes in poker's
  binary, which is what a generalisation is worth here.
- **The deck no longer carries its own generator.** Poker's version had
  an injectable RNG *and* its own copy of the rejection-sampling bound,
  which is how the tree ended up with two implementations of the same
  arithmetic, both wrong in different ways. `zdeck` calls
  `zg_rng_below()`.

## The bank: `/USER/casino.dat`

It lives under `/USER`, with the rest of what belongs to the person
rather than to the system.

**The directory is created on demand, not by the image builder.** A save
tries the write first and only calls `fs_mkdir()` if it fails —
creating it eagerly would be a directory lookup per round for a
condition that is true once in the life of a card. `fs_mkdir()`'s own
result is not checked: if it failed because the directory already
exists the retry is right anyway, and if it failed for any other reason
the retry reports it.

**`zbank_load()` falls back to `/casino.dat`**, where the bank used to
be, so an existing bankroll survives the move. The next save writes the
new location, after which the old file is a stale copy. A card with both
has already been saved since the move, so the new one is the live one.

One pile of chips that every game spends from and pays into, so winning
at roulette leaves you better off at blackjack. Without it each game is
a sealed world and the chips mean nothing.

### Apply a delta, never write a balance

This is the whole design and everything else follows from it.

Two games can be open at once. If roulette writes `chips = 940` from a
copy it read two minutes ago, it silently erases whatever poker won in
between — and neither app has done anything obviously wrong.
`sw/common/zfsapp.h` flags exactly this concurrency caveat for the
syscalls underneath.

So the operation a game performs is `zbank_adjust(game, delta)`, which
re-reads the file, applies the change to whatever is there *now*, and
writes that back. A stale in-memory copy then costs nothing. The
remaining window is the few milliseconds between that read and that
write, and two games would have to land inside it on the same tick.

**There is no `zbank_set_chips()`, and that omission is deliberate.** A
function that can write an absolute balance will eventually be called
with a stale one.

### The file

```
# Zeitlos casino bank -- chips shared by every game.
version: 1
chips: 1000
peak: 1450
buyins: 1
game.roulette.net: -120
game.roulette.rounds: 40
```

Text, in the same `key: value` shape as `/zeitlos.cfg`, so `cat
/USER/casino.dat` from the console tells you something and a hand edit is
possible when a game gets it wrong. Binary would be smaller and would
make both of those false.

### What happens when it is damaged

**Parsing is lenient.** Unknown lines are ignored, missing keys take
their defaults, and a file truncated by a power cut still yields
everything before the cut. A future game writing a key this build does
not know must not brick the bank for this one.

**A file that exists, is not empty, and has no `chips:` line at all is
treated as corrupt rather than as a fresh bank.** `zbank_load()`
reports it and `zbank_adjust()` refuses to write over it. Overwriting a
real balance with a default one is the single unrecoverable outcome
here, so it is the one case that fails loudly instead of quietly
carrying on. A missing file is *not* corrupt — that is a first run, and
the defaults are right.

### Two halves

The parser, the formatter and the arithmetic are pure: no filesystem,
no syscalls, host-testable. The load/save/adjust wrappers are the thin
part that touches `zfsapp`. Same split `sw/common/zcfg.h` uses, and for
the same reason — the interesting logic is the part that can be tested
without a device.

`zbank_load()` reads into a static buffer rather than using
`fs_mallocfile()`. An app's heap and stack share one 16KB allowance and
`_sbrk()` refuses to grow into the stack, so a few KB of `malloc` can
fail on the device while succeeding on any build machine.
`sw/apps/settings` found that reporting "out of memory" when saving.

### What the tests prove

Round trips, including a bank with every game slot full. Lenient
parsing of comments, blank lines, all three separators, unknown keys
and non-numeric values. A corrupt file recognised as corrupt. A
truncated file — cut at every offset from 40 bytes to the end —
parsing or reporting damage, never producing a negative balance.
Balances flooring at zero. A ninth game into eight slots not
overrunning the table. And the formatter refusing rather than writing
past the end, checked at *every* buffer size from zero upward with
guard bytes either side.

`ZBANK_FILE_MAX` was 512, chosen by eye, and eight games did not fit —
the formatter refused and the bank could not be written at all once the
last slot filled. The test now fills every slot with the longest values
the fields allow, so the constant is pinned to the documented maximum
rather than to a guess.

## The bounded draw

`zg_rng_below(n)` exists because **`z_rng_below()` does not return when
`n` is a power of two.** It computes its accept bound as
`2^32 - (2^32 % n)`, which for such an `n` is exactly `2^32`, and that
truncates to **0** in the `uint32_t` holding it — so
`while (v >= limit)` on an unsigned never ends.

It is not hypothetical. A 52-card Fisher-Yates asks for bounds of 52
down to 2 and hits 32, 16, 8, 4 and 2 on every shuffle;
`sw/apps/poker` hung on its first deal before it had drawn anything,
which presented as a blank window and wm timing out on a redraw.
`sw/apps/repl`'s `(random 16)` has the same exposure.

The case the original arithmetic cannot express is the one that breaks
it: when `n` divides 2^32 there is nothing to reject, and the accept
bound would be `2^32`, which does not fit in the type it has to live
in.

If `z_rng_below()` is fixed, this should stay anyway. One tested
implementation that every game shares is the point; the bug is what
made it urgent, not what makes it worth having.

### The source is injected

Nothing in `zrand.c` calls into Zeitlos, so the tests can install a
source that hands out chosen words and observe exactly which ones get
rejected. That is the only way to see the accept region from outside,
and the accept region is where the bug lived. The tests assert the
boundary exactly — for `n = 3`, precisely one word is thrown away; for
`n = 37`, precisely seven; for any power of two, none.

The fake source aborts after a thousand draws, so a broken bound
produces a named failure rather than a hung test. A hung test looks
like a slow machine and gets killed; a failing one says what is wrong.

`zrand_sys.c` wires it to `sw/common/zrng.c`'s generator. An app calls
`zg_rng_use_system()` once at startup; one that forgets gets a
fixed-seed fallback that deals the same first hand every boot —
deliberately obvious in seconds rather than subtly wrong forever.

### On the TRNG

`z_rng_bytes()` **is** the TRNG path: `zrng.c` hashes 256 bytes of
`rtl/trng.v` into a ChaCha20 key and every byte the system uses comes
from that at memory speed. Nothing extra is needed to "use the TRNG".

What varies is whether the seed was hardware or cycle-counter jitter,
which `z_rng_secure()` reports. **Games should not gate on it.**
`zrng.h` states the rule plainly: shuffling and games want
unpredictable-to-a-person; keys and nonces check and refuse. Refusing
to spin a wheel on a board without a TRNG treats a casino game like a
key exchange.

The useful thing to do with that bit is *show* it. A game can ask
`z_rng_secure()` and put it on the table, so the person knows whether
the wheel is hardware-seeded rather than having to assume.
